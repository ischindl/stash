Proof 2 - the same files move in and out of the failing set at a single unchanged revision. The seven

  files failing in the union run          pass 1              pass 2

So at one fixed commit the failing set of these files is not reproducible run to run. A hash over a
full-suite failing set is therefore not a measurement of code on this host at this wallclock: it
measures the load of the run. That is what section 2's NONZERO hash comparison means, and it is why
the attributable-regression count is computed per file below rather than by the hash.

Proof 3 - each of the two has a mechanism that does not involve this card.

  remote-node-runtime.test.ts > "treats an answer that arrives after the probe budget as no answer"
    The test installs `vi.useFakeTimers()` after `await runtime.start()` and then races a never-
    resolving promise against `advanceTimersByTimeAsync(INFLIGHT_PROBE_TIMEOUT_MS)`. Its failure mode
    is a 30000 ms timeout, which is what a fake-timer race loses when the process is starved. The
    module under test imports `node:events`, `@fusion/core`, `scheduler`, `project-runtime`,
    `isolation-transition-blockers`, `logger` and `remote-node-client`; this card edits none of them.

  self-healing-stranded-deferral-horizon.test.ts > "records every saturated pass as an event row..."
    This one is a knife-edge in the fixture, and the arithmetic closes:
      the sweep   self-healing.ts:12893  stalenessMs = max(0, now - updatedAt)
      the judge   stranded-continuation-reclaim.ts:387-388
                    stoppedAt    = input.now - input.stalenessMs      (== the row's updatedAt)
                    priorWidthMs = Date.parse(item.retryAfter) - stoppedAt
                  :405-406  rungSaturated = priorWidthMs >= TOP_RUNG
      the fixture self-healing-stranded-deferral-horizon.test.ts:155 sets
                    retryAfter = Date.now() - STALE + TOP_RUNG          (read A, at the call site)
      and the same file's :68 default sets
                    updatedAt  = Date.now() - STALE                     (read D, inside the builder,
                                                                         evaluated after the arguments)
      therefore  priorWidthMs = TOP_RUNG - (D - A), and `rungSaturated` - the only thing that emits
                 `workflowWorkItem:reconcile-stranded-defer-sustained` - is true iff A and D land in
                 the SAME MILLIMETRE.
    The observed failure text is `AssertionError: expected [] to have a length of 1 but got +0` at
    that file's line 161: no sustained row, because the row was one millisecond short of "saturated".
    A loaded machine separates the two `Date.now()` reads by a millisecond; an idle one does not.
    Neither this test file nor `stranded-continuation-reclaim.ts` is in this card's diff, and the
    file's last commit is `7eb5aed394 RUFU-299`, not this card. REPORTED as a pre-existing defect
    worth its own card: a test whose predicate holds only when two clock reads share a millisecond
    will mis-signal for every future engine card that runs the full suite.
