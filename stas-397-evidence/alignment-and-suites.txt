1. PARTICIPATING COMMAND FORMS — the number AC5 turns on
--------------------------------------------------------
"Participating" means: a `git status` read whose answer decides whether an already-merged checkout
holding ONLY gitignored content gets released. That is the question the wedged seven are stuck on.

  BEFORE (base 46b94afa0c) — 2 forms, and they disagreed:

    a) worktree-backend.ts:1371  `git status --porcelain=v1 --ignored=matching --untracked-files=normal`
       Answer for a wedged checkout: `ignored-only` -> removeWorktree THREW
       "preserving <path>: uncommitted or ignored content present" (line 1755). BLOCKED the release.
    b) execution/branch-conflicts.ts:1539  `git status --porcelain` (bare)
       Answer for a wedged checkout: empty stdout -> "clean". ALLOWED the release.
       Its four callers are the doors that lead to that release:
         self-healing.ts:6361, executor/worktree-branch-conflict-handle.ts:197,
         executor/worktree-create-conflict.ts:405, auto-recovery-handlers/branch-worktree.ts:547.
       Two predicates, one tree, opposite answers, in the same sweep: the door said the checkout was
       empty and the removal said it was not, and the removal won by throwing.

  AFTER (tip 3ab0e55698) — 1 form:

    a) worktree-backend.ts:1351  the same vector, unchanged argv, now the ONLY read that decides it.
       Answer for a wedged checkout: `ignored-only` -> releases, and records the discard by name.
    b) `taskWorktreeCheckoutIsClean` no longer runs a command. It is defined next to the predicate and
       returns `content.status === "classified" && content.classification !== "deliverable"`, so the
       four doors ask the probe. The bare `git status --porcelain` in branch-conflicts.ts is gone
       (raw/ac5-counts.txt shows the only remaining hit there is a comment naming the relocation).

  Its answers are identical to before, which is what makes the alignment safe:
      clean          -> true      (was: empty porcelain -> true)
      ignored-only   -> true      (was: ignored excluded by the bare read -> true)
      deliverable    -> false     (was: non-empty -> false)
      probe-failed   -> false     (was: exec threw -> false)
      path-absent    -> false     (was: exec threw -> false; all four call sites are behind existsSync)
  The guard test covers the ignored-only row for real; the four doors are covered by the existing
  suites (`raw/` logs below and before-after-suites.txt).
