    STAS-335: make store boot and query failures name their stage, table, and SQLSTATE

A stalled TaskStore boot reported only the budget it burned, and a failed board
read reported its entire SQL statement and no reason. Neither was diagnosable
after the fact: the factory's per-stage timings went to console output, which
the forked extension runtime discards (silent: true, IPC-only), and the engine's
read-path error seam carried no table, no SQLSTATE, and no read/write class.

Carry the attribution in the values that actually travel:

- startup-factory: report each boot stage through an optional onBootStage
  observer, matching the existing onMigrationProgress precedent.
- extension: collect the stages per attempt, attach them to
  TaskStoreBootTransientError and to the cooldown entry, and surface them in the
  tool result. The tool result is the durable channel because it is recorded in
  the agent log, unlike the console line.
- tool-store-errors: recover table, statement kind, and SQLSTATE from a
  DrizzleQueryError by reading `query` and `cause` structurally. `params` is
  deliberately never read: bound values are user content and must not reach a
  tool result or an agent log. Label read vs write explicitly.

The transient class is unchanged — a genuine boot failure stays fail-closed
(STAS-299 Invariant B) — and teardown ownership is untouched: factory-owned
entries are shut down, host-injected entries are not.

Tests: 9 CLI + 11 engine. The regex fix the tests forced (a two-optional-group
form returned "s" for "tasks") is pinned by a case for each quoting shape.
