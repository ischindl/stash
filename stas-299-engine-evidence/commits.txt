core: answer *why* a card is not the stranded-gate retry class

A retry surface that refuses can only be trusted if it says why. `classifyStrandedGateRetry`
returned a bare `null` for six structurally different refusals, so every surface (board Retry, CLI,
chat tool) would have to re-derive the reason to explain itself — the same duplication this module
exists to remove.

The classification is now a discriminated union: `{kind:"stranded-gate", gateStepIds}` or
`{kind:"not-stranded", reason}`, where the reason names the leg that failed — legacy board with no
column model, column not on the board, a lane that owns its own recovery (WIP/review/complete), a
status another lane wrote (replan/approval/merge keeps its path), no approved plan, or no verdict-less
required gate. The refusal set is also what lets a surface tell "not this class" from "malformed
request".

engine: a failure park owns the card until a retry discharges it

STAS-299's first half stamps a hold-lane card `failed` when self-heal has to fail its orphaned gate
row. That only fixes the dead zone if the park is real, and it was not: the stranded-hold continuation
sweep — the recovery owner that re-arms a gate with no live session — reads a hold-lane card with an
approved plan and no satisfied review as exactly that shape, so within one sweep interval it would
have re-seeded Plan Review on the card the sweep had just parked. A park the engine immediately
re-runs is an auto-retry wearing a different hat, and the spec's whole point is that this shape gets a
deliberate owner.

Both seams now name the owner instead of acting: the evaluator and the seeder bail `retry-owned` (the
same "another owner holds this card" family as `triage-owned`) for a card whose status is a failure
park, the runtime treats it as a quiet park rather than a seed failure worth warning about, and an
explicit plan approval — an operator action, so an honest exit from the park by the same rule that
makes an operator retry clear a skip-bypass taint — discharges the status inside the planning
lifecycle fence before arming the gate.

Proved both ways: the sweep leaves a parked card untouched and re-seeds the moment the status is gone;
the evaluator reports `retry-owned` parked and `ready` after; approval resumes; self-heal parks once
(no re-stamp, no re-audit) and leaves no card in the forbidden shape when judged by the classifier the
retry surfaces consume.

cli: a stalled TaskStore boot answers with a retry, not a denial (STAS-299 req 3)

The incident sentence an agent got when its escape hatch was slow:

  fn_task_retry denied: the agent permission policy could not be resolved (fn extension
  TaskStore boot timed out after 30000ms). Failing closed — ask the operator to run this tool.

STAS-281, twice. No permission was involved: the store open in a second backend inside a live
dashboard process simply burned its budget, and the boot kept running. Two separate claims got
merged into one verdict — "this cannot be answered right now" and "you are not allowed" — and the
merged form forbade the only action that works, because the next call is served from the boot already
in flight. The read path had the mirror defect: fn_task_logs_read returned the raw boot sentence with
nothing actionable in it.

A stall is now its own class, `TaskStoreBootTransientError`, raised from the two branches that produce
it and nowhere else: the wall-clock budget expiry, and the cooldown entry a deadline leaves behind
(marked `fromDeadline`). One fingerprint defines the class — the shipped `timed out after Nms` marker
that `getStore` already records as `"outcome":"deadline"` — so the answer an agent gets cannot
disagree with the record an operator hunts. A boot that failed for a reason other than waiting stays
untyped, keeping RUFU-275's honest fail-closed denial under `taskstore-boot-unavailable`.

Every surface answers a stall with the same built result. The first line keeps RUFU-377's attribution
contract exactly (`X failed: ` prefix + the store-boot subject), and the retry instruction rides below
it: retry this call, nothing was denied on policy grounds, nothing was lost, do not ask the operator.
Two shipped expectations in the agent-class boot suite were updated to pin both lines, because the
bare deadline sentence they used to anchor is precisely what STAS-281 measured as unactionable.

RUFU-377's shipped contract is otherwise untouched: same messages, same telemetry, and a caller
arriving inside the backoff window is still answered in milliseconds instead of re-paying the boot
budget — it is simply typed as the same stall rather than as a fresh failure.

STAS-299 requirement 3.

STAS-299: answer a tool's own budget expiry as the tool's failure, and let a retry report name the lane it resolved

Code review retry 3 found two defects in what this branch ships. Both are
fixed with a failing test first, each verified red against the pre-fix code
and green after.

P0 — the stall answer was reachable by a tool that merely ran long.
`raceWithTimeoutAndAbort` builds its sentence as `<label> timed out after
<N>ms` and `wrapExtensionToolExecute` passes `label = toolName`, so
`fn_task_merge timed out after 60000ms` carries the byte-identical
fingerprint of the store boot's own deadline sentence. Because
`isTransientStoreBootFailure` classified by that sentence, every tool-budget
expiry — including one that stopped a possibly-mutating tool half-applied —
answered `transient: taskstore-boot-timeout, retryable: true, the boot is
still running in the background, nothing was denied`. That is a verdict about
an operation whose effects nobody knows. The predicate is now the TYPE: the
narrowing loses nothing because `getStore` raises the typed error on both of
its transient branches (the deadline and the cooldown it arms), and those are
the only two paths either answer site can meet. The message fingerprint keeps
the two jobs it is honest about, both inside the boot itself: the transient
branch in `getStore`'s catch, which sees only boot errors, and the
console-stream choice in the wrapper, which changes loudness, never what the
agent is told.

The pre-existing timeout test could not see this because `toMatchObject`
ignores the extra fields the stall path adds; the new test pins the absent
fields, not just the present ones.

P1 — a retry reported a lane the card did not go to. Both `fn_task_retry`
re-queues moved the card to the resolved hold lane and then answered
`details.newColumn: 'todo'`, a machine-readable field another tool can act
on, while the `logEntry` line wrote the same literal into the card's audit
trail; a third branch moves nothing and still answered `in-review`. The CLI
`fn task retry` had the same gap in its log line and terminal output. Now the
target resolves before the log line and every report — log, reply text,
payload — carries that one resolved value, matching the dashboard route, which
resolved before logging from the start. `extension.test.ts` cannot catch this
class: every retry fixture there sits on `builtin:coding`, whose hold lane IS
`todo`, so pre-fix and post-fix bytes agree. The new test file pins it on a
board that renames all three lanes.

Docs: the architecture boot-budget section said `isTransientStoreBootFailure`
fingerprints the deadline shapes; it now says what actually classifies, and
why the shared `<label> timed out after <N>ms` suffix is the reason an answer
site may not key on the sentence.

Verification: new P0 test fails pre-fix, passes post-fix; the typed-stall test
in `extension-store-boot-transience.test.ts` passes on both, which is the
point — narrowing must not lose a real stall. All 3 new P1 tests fail pre-fix,
pass post-fix. `pnpm typecheck` clean, eslint clean on all touched files,
`pnpm test:gate:static` green, `check:move-target-literals` population still
empty. CLI package suite: 15 failures measured IDENTICAL with and without this
