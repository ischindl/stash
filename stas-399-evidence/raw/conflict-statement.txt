THE TRAP: THAT ONE LINE IS NOT THE WHOLE EFFECT, AND SAYING SO IS PART OF AC7
  It moves the prompt clamp AND the engine's own write-side reject (`agent-tools.ts` now imports the
  constant, so `fn_update_identity` accepts 65,536 the same moment the clamp does -- that coupling is this
  card's doing and is the honest consequence of "one number, one definition").
  It does NOT move the four dashboard write guards, which hold the literal `50000` in their own packages:
    packages/dashboard/app/components/AgentDetailView.tsx:3155
    packages/dashboard/src/routes/register-agent-core-routes.ts:295
    packages/dashboard/src/routes/register-agent-core-routes.ts:854
    packages/dashboard/src/routes/register-agent-runtime-routes.ts:265
  A ruling applied as one line would therefore let the engine's own tools write 65,536 chars of memory while
  the dashboard UI still refuses the same edit at 50,000 -- an asymmetry between two write paths, not between
  two budgets. Any ruling must name those four sites in the same breath. (carrier-census.txt PART 4 said
  "three dashboard guards"; four is the measured count in numeral-census.txt PART 3 -- corrected here rather
  than repeated.)
  It also does not touch the 32 KiB BYTES consolidation budget, which is the number that decides WHEN an
  agent's own maintenance consolidates a file. Raising [4] without touching [2] means agents are consolidated
  to a 32 KiB working set and then allowed to render 64.5 K chars of it: the consolidation incentive does not
  disappear, it just stops being the binding constraint on prompt size.
